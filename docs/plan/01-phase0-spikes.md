# Phase 0 — Technical Spikes (S1–S4)

Goal: measure the 3 product-killing risks (insertion reliability, Japanese STT quality, E2E latency) **before** writing production code. Deliverables are measurement data + confirmed provider selection, not shippable code. Write throwaway harnesses under `spikes/`, but design the STT/LLM adapters and the golden-set harness so they can be promoted into Phase 1 (M4/M6).

Each spike has a numeric Go gate (Design §12.1). Do not start Phase 1 milestones that depend on an unresolved gate (M4 depends on S2, M6 prompt tuning depends on S3; M0–M3, M5 can start in parallel with S2–S4).

Results recording: append measured values to each spike section below and to the design doc (§6 appendix for S1). Update `[tune in Phase 0]` constants in the plan docs.

## S1 — Insertion matrix

Validate paste-simulation insertion across target apps and fix the timing constants.

### S1-T1 Build insertion harness

- Minimal macOS app or CLI (needs Accessibility permission): given a text argument, run the full path-1 insertion sequence from `03-phase1-m2-pipeline.md` M5 (clipboard snapshot → write with `org.nspasteboard.TransientType` / `AutoGeneratedType` / `source` + session-UUID type → 100ms pre-delay → synthetic Cmd+V via `CGEventSource(stateID: .privateState)` posted to `.cghidEventTap`, 10ms between events, V keycode resolved via `UCKeyTranslate` → best-effort AX verification → restore snapshot after 300ms if UUID marker still present).
- Also implement path 2 (AppleScript `keystroke "v" using command down` via System Events) as a switchable mode.
- Configurable pre-delay and restore-delay flags for tuning.
- Acceptance: harness inserts into TextEdit and Slack; clipboard content prior to run is restored afterward; Maccy/other clipboard managers do not record the inserted text.
- Design ref: §6.3, §6.5.

### S1-T2 Run the matrix

- Apps (15–20): Slack, Chrome (Gmail, Google Docs), Safari, Mail, Notes, Notion, VS Code, Cursor, Terminal, iTerm2 (running Claude Code), TextEdit, Word, Excel, Messages, Discord, LINE, System Settings search field, 1Password (expected refusal).
- Cases per app: normal insert / 1,000-char insert / insert while IME composition is active (Kotoeri and Google Japanese Input) / ⌘Z immediately after insert (must undo cleanly).
- Record: success per path, minimum reliable pre-delay, side effects (sound, focus/scroll jumps), whether AX verification is readable.
- **Go gate**: path-1 alone ≥95% on major apps; ≥99% including path 2. IME and Secure Input behavior documented.
- No-Go branch: tune per-app delays, widen AppleScript path coverage, re-measure.
- Design ref: §6.5, §12.1.

## S2 — STT A/B (Speechmatics vs Deepgram Nova-3 vs Soniox v5)

### S2-T1 Utterance set + streaming harness

- Build a fixed audio set: 50 pure-Japanese, 30 ja-en mixed (product/tech terms inline, e.g. 「Claude Codeでデプロイして」), 20 dictionary-term utterances. Record once (16kHz mono), reuse across providers.
- CLI harness streams a WAV in real time over each provider's WebSocket API, requests manual end-of-utterance at EOF, records: final transcript, key-up→final latency, partial-transcript latency. Run from a Japanese residential/office network; note the region endpoint used (Speechmatics EU RTT is a known concern).
- Provider settings: keyword boost / `additional_vocab` / Context fed from the same 20-term dictionary; smart formatting/ITN **off**; Deepgram `mip_opt_out=true`.
- Design ref: §4.1, §8.

### S2-T2 Evaluate

- Metrics per provider: (1) pure-JA character error rate, (2) ja-en mixed fidelity (are English terms recognized or at least consistently katakana-ized so dictionary+LLM can restore them — judge the **pipeline** outcome, not STT alone), (3) dictionary boost effect, (4) finalization latency.
- **Go gate**: at least one provider is practical including mixed speech. If all fail on mixing, test whether dictionary + LLM restoration meets the bar; if not, escalate to the owner (lower the mixed-speech requirement or delay).
- Output: pick primary + runner-up; record decision and data here.
- Design ref: §4.1, §12.1 (S2), risk R4.

## S3 — LLM golden set (Gemini 2.5 Flash-Lite vs Claude Haiku 4.5)

### S3-T1 Golden set v1 (~150 cases)

- 10–20 cases per formatting category (Design §5.3): 1 filler removal, 2 self-correction merging, 3 repetition compression, 4 particle completion, 5 style unification (desu/masu ⇄ dearu), 6 punctuation/paragraphing, 7 list conversion (**include must-NOT-convert cases**), 8 ITN (dates/numbers/units; keep idiomatic kanji numerals like 一石二鳥), 9 ja-en term restoration (「クロードコード」→「Claude Code」 via dictionary), 10 voice command 「かいぎょう/改行して」→ newline (only this one command).
- Plus compound cases and >500-char long-form cases. Case format: `{input transcript, style setting, dictionary, expected output or rubric}`. Store as JSON/YAML in-repo (this is a durable asset → Phase 1 regression harness).
- Design ref: §5.3, §5.5.

### S3-T2 Regression harness + A/B run

- CLI runs the golden set against a configured `LLMClient`; two-stage judging: (a) deterministic checks — non-empty, no preamble/quotes, no prompt-instruction leakage, output/input length ratio (summarization suspicion >30% shrink fails), dictionary spelling compliance; (b) LLM-as-judge (a different model) scoring intent-preservation / formatting adequacy / no over-formatting on a 3-point scale.
- Run with the v1 prompt (see M6) on Flash-Lite (thinking disabled) and Haiku 4.5; also measure TTFT and tok/s from Japan, and whether prompt caching applies (Haiku needs ≥4,096-token prefix; likely not — confirm).
- **Go gate**: one model passes — zero critical violations (intent alteration, over-formatting), judge pass ≥90%. Flash-Lite passing ⇒ it wins on latency/cost; otherwise Haiku.
- Design ref: §4.2, §5.5, §12.1 (S3).

## S4 — E2E latency prototype

### S4-T1 Wire and measure

- Thin pipeline connecting the S1 inserter + S2-selected STT + S3-selected LLM (harness quality; hotkey can be a keyboard shortcut in a debug app). Timestamps: `t_keyup, t_stt_final, t_llm_first_token, t_llm_done, t_insert_done`.
- 100 real utterances from a Japanese network; compute per-segment P50/P95 against the budget table in `00-overview.md`.
- **Go gate**: E2E P50 ≤2.0s (prototype relaxation; must show a credible path to 1.5s in production).
- No-Go branch: switch provider region (Tokyo/APAC), consider speculative formatting (launch LLM on the last partial transcript at key-up), re-measure.
- Design ref: §8, §12.1 (S4).
