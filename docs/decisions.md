# Decision log

## 2026-07-09 (session 12 — full-codebase review, batch A: insertion)

Owner directive: review the entire codebase batch-by-batch (A–F), fix confirmed findings, no approvals. Batch A = PasteSimulator + KoeCore/Insertion + serializer + context provider + key resolver.

- **`runAppleScriptPaste` installs `terminationHandler` before `run()`.** A handler assigned after the process exits is never invoked — the continuation would stay suspended forever and stall the insertion FIFO (data-loss-class). Launch failure resumes the same continuation with `launched == false`; no double-resume is possible (a process that never ran can't fire the handler).
- **Paste choreography is now cancellation-safe.** `try? await Task.sleep` silently no-ops when the task is cancelled, collapsing the timing chain: a skipped pre-delay could post Cmd+V before the clipboard write propagates (pasting stale content); a skipped settle ran verify/restore too early. Now: cancelled pre-delay → `.advance` without posting (payload stays; the chain degrades to the clipboard landing, which posts nothing); the settle sleep is shielded in an unstructured child task so verify + marker-gated restore always complete once the keystroke is out (an early restore would paste the OLD content; skipping restore would permanently clobber the user's clipboard — review finding).
- **AX reads bounded via process-wide messaging timeout (`axReadTimeout`, 1s).** The ~6s system default let one unresponsive target app freeze the main actor (hotkeys, UI) for multi-second stretches per read. 1s, not the 250ms first tried: timed-out secure-field/verify reads fail *open* (proceed / assume success), so an aggressive bound silently weakens the invariant-3 secure guard and the invariant-1 verify net for slow-but-alive apps (heavy Electron ~400ms) — review finding. The system-wide `AXUIElement` is created once and reused.
- **Reviewed, accepted as-is (documented here as the audit trail):** `postCmdV` partial CGEvent-creation failure still reports success (unreachable in practice, and distinguishing "V-down failed" from "V-up failed" is what decides paste-vs-no-paste); re-entrancy guard returns `.clipboardFallback` without writing the clipboard (only reachable from DEBUG QA hooks — production is serialized by `InsertionSerializer`); verify false-negative → path-2 double-paste risk is the documented best-effort trade-off; `InsertionSerializer.complete` keeps its `precondition` (structural exactly-once release in the coordinator, unit-tested).

### Batch C — audio capture (no behavior bugs found; no code change)

- **Reviewed clean:** `AudioCaptureEngine` (start/stop/cap/route-change state machine; failure paths always end the stream and the App Nap activity; tap rebuild only while the engine is stopped), `TapState` (`@unchecked Sendable` justified — tap-thread-only mutation, buffer carried over only after stop), `AudioDeviceObserver` (main-queue HAL listeners + `assumeIsolated`, cached enumeration, CF property memory handling correct), `InputDeviceSelector`/`SessionAudioBuffer`/`AudioFormatSpec` (pure, tested; cap-boundary math exact — a chunk landing exactly on the cap is kept in full and caps).
- **M9 note:** `handleRouteChange` failure paths reuse `onCapReached()` as a generic "recording ended unexpectedly" reset. Today that only resets the status icon; once M9 builds the HUD, the cap callback will carry a "20-min limit" message — the device-switch-failure path must get its own callback (or a reason parameter) or users will see the wrong explanation.

- **Chain ordering is pure and fault-injection-tested; system work is the adapter's.** `InsertionChain.run(paths, attempt:)` walks a plan and stops at the first `.landed`, with a `.clipboardFallback` floor; the per-path system work (paste / AppleScript / clipboard) is the app-layer `attempt` closure. This puts the reviewer's acceptance case — "block path 1 → walk to path 3" — into a KoeCore unit test with no system APIs. `InsertionPathPlanner.plan(preferred:)` always ends at `.clipboardOnly` so the chain can never fall off the end with text lost (invariant 1).
- **`InsertionChain.run` takes `isolation: isolated (any Actor)? = #isolation`.** The `attempt` closure captures the `@MainActor` `PasteSimulator`; a plain non-isolated static func would reject it as a data race (or force `@Sendable`, which then can't capture the test's mutable recording array). Inheriting the caller's isolation lets both the MainActor adapter and the non-isolated test drive it.
- **Path 2 runs `osascript` as a bounded subprocess, not `NSAppleScript` on the main thread.** `tell application "System Events" to keystroke "v" using command down` via `/usr/bin/osascript`, awaited through the process `terminationHandler`; a watchdog `Task { @MainActor }` terminates it if it overruns `insertionStageTimeout` (e.g. a blocked Automation-permission prompt) so the chain advances instead of hanging. Exit 0 = delivered. (App Sandbox is off, so `Process` is available; needs Automation TCC for System Events — owner QA.)
- **A failed path advances without restoring.** Write-fail / keystroke-post-fail / explicit verify-fail all return `.advance` and deliberately leave the marked payload on the clipboard so the next path (or the path-3 landing) still has the text. Restore only runs on a landed paste, and only if our session marker still owns the clipboard.
- **Per-app overrides are a pure `InsertionOverrideTable` (bundle id → preferred path + extra pre-delay), injected empty.** Settings (M10) will populate it; no wildcard, unknown app ⇒ plain path 1. `extraPreDelay` is added to the pre-paste sleep. Runtime override behavior is validated once M10 ships the editor; the resolution + planning are unit-tested now.
- **3 DEBUG QA menu items force each path** (`debugInsert(_:forcing:)`) so the owner can exercise path 1/2/3 landings by hand before the STT→format→paste pipeline is wired. Secure-input block is still honored in the QA path; the app-change guard is skipped (no recording app in QA).

### M5-T3 code-review fixes (high, 2 distinct findings)

- **Clipboard snapshot hoisted above the whole chain** (findings [0]/[1]/[2] — the same bug reported thrice, confirmed). `pasteViaKeystroke` used to re-`snapshotItems` on every attempt. Since a failed path deliberately leaves its marked payload on the clipboard (no restore) and advances, path 2's fresh snapshot captured path 1's *leftover marked payload* — so a successful path-2 restore wrote that back instead of the user's real original clipboard, silently clobbering it. Fixed by snapshotting once in `runPlan` before any write and threading the single `originalSnapshot` through `attempt`→`pasteViaKeystroke`; the per-attempt session-marker ownership check is unchanged. (The single-path M5-T2 code couldn't hit this — the chain retry introduced it.)
- **`beginInserting()` returns `Bool`, not `Void?`** (finding [3], cleanup). The `guard let _ = beginInserting()` dance was replaced with a plain `guard beginInserting()`.

## 2026-07-06 (session 10 — M5-T2 paste simulation path 1)

- **Pure/adapter split (same pattern as M3/M5-T1).** KoeCore gets the testable pieces — `PasteboardMarkers` (marker type ids + per-paste session-UUID type), `PasteTextPreparer` (terminal-family detection + trailing-newline strip + interior-newline warn), `PasteVerification` (best-effort AX verdict) — with +13 tests. The untestable system glue is `App/PasteSimulator.swift` (NSPasteboard/CGEvent), `App/InsertionContextProvider.swift` (Secure Input / AX subrole / NSWorkspace reads), `App/PasteKeyResolver.swift` (TIS/UCKeyTranslate).
- **`\r\n` grapheme trap.** Swift treats CRLF as one `Character`, so the naive `last == "\n" || last == "\r"` trailing-strip left a `\r\n` behind (caught by a test). Strip via `Character.isNewline` and detect interior breaks via `contains(where: \.isNewline)` — both handle the combined grapheme.
- **Verification reads AX *after* the 300ms restore wait, not immediately.** The dwell window doubles as a settle window so the paste has time to land before we read `AXValue`/`AXSelectedText`, cutting false failures. Unreadable AX (Electron, no tree) ⇒ `.unverifiable` ⇒ assume success (no clobber); only an explicit `verifiedFailed` (readable focus lacking the inserted tail) leaves the marked text on the clipboard as the fallback landing (`.clipboardFallback`) — restoring there would drop text the paste failed to insert.
- **Restore only if the session marker survives** (Design §6.3-6): if our private session-UUID pasteboard type is gone at restore time, another process wrote the clipboard in the meantime, so we skip restore rather than clobber it.
- **Path 2/3 deferred to M5-T3, but the landing is safe now.** M5-T2 ships path 1 only; a secure context blocks (no insert, no clipboard — invariant 3), and app-change/verify-fail leave the marked payload on the clipboard for a manual ⌘V. The pure `PasteVerification` verdict is delivered and tested so M5-T3 wires the AppleScript escalation onto the existing `verifiedFailed` branch.
- **`recordingBundleID` is an injected closure, not the `TextInserting.insert` signature.** The preflight app-change guard needs the frontmost bundle id captured at record start; the seam doesn't carry it, so `PasteSimulator` takes a `@Sendable () -> String?` (coordinator sets it later). The DEBUG QA menu item passes `{ nil }` so it pastes wherever the owner puts the cursor (pipeline isn't wired end-to-end yet).

### M5-T2 code-review fixes (high, 6 findings)

- **Empty-after-prep payload no longer claims `.pasted`** (finding [0], confirmed). An all-newline terminal dictation strips to `""`; the old path pasted an empty clipboard and, because the verification needle was empty (`.unverifiable`), reported `.pasted` — silent content loss. Now `pasteSimulation` short-circuits an empty prepared payload: truly-empty raw → `.pasted` no-op; non-empty raw (terminal newlines stripped away) → leave the **raw** text marked on the clipboard for a manual ⌘V and return `.clipboardFallback` (no auto-paste of the newlines).
- **Re-entrancy guard on `performInsert`** (finding [1], confirmed). Two overlapping insertions would snapshot each other's marked payload and clobber the user's real clipboard on restore. An `isInserting` flag (check-and-set atomic on the main actor) skips a re-entrant call. Production is already serialized by `InsertionSerializer`; this backstops the repeatable DEBUG QA hook.
- **`NSPasteboard.writeObjects` Bool return is checked** (findings [2]/[3], plausible). `writePayload`/`putMarkedText`/`restore` return the write success. A failed initial payload write aborts before Cmd+V (never paste stale content) and lands on `.clipboardFallback`; failed clipboard-hold/restore writes log a distinct event instead of failing silently.
- **Focused-AXElement and frontmost-app lookups deduped** (findings [5]/[6], confirmed cleanup). `InsertionContextProvider` now owns a single `focusedElement()` helper feeding both `focusedFieldSecure()` and `focusedValueSnippet()`, and the async `frontmostBundleID()` seam delegates to the sync `currentFrontmostBundleID()`. `PasteSimulator.verify` calls `context.focusedValueSnippet()` instead of re-implementing the AX dance.
- **Overlapping-utterance limitation documented, not yet fixed** (finding [4], plausible/unwired). The single `recordingBundleID` closure can't distinguish two concurrently-recording utterances; since the coordinator isn't wired to `PasteSimulator` yet, this is a documented M5-T3 prerequisite (thread the per-utterance recording bundle id through `UtteranceContext`), called out in both the code and above.

## 2026-07-06 (session 9 — M3-T2 device-switch survival)

- **Pure/adapter split (same as M3-T1).** `InputDeviceSelector` + `AudioInputDevice` in `KoeCore` decide which input device to record from (`select`) and whether a mid-recording route change warrants switching (`resolveSwitch`), unit-tested (+11); the untestable CoreAudio enumeration/listener glue is `App/AudioDeviceObserver.swift` and the device-pinning/tap-rebind lives in `AudioCaptureEngine`.
- **"Prefer built-in mic" default ON, implemented by pinning.** macOS otherwise follows the system default onto a freshly-connected Bluetooth headset (HFP, degrades STT). The engine pins the selected device via `kAudioOutputUnitProperty_CurrentDevice` on the input node's audio unit, so a headset connecting mid-session does **not** steal capture. The pref is a `preferBuiltIn: () -> Bool` closure re-read each start (UserDefaults key `preferBuiltInMic`, default true) so a future Settings toggle needs no engine rebuild.
- **Device-switch continues the same session (invariant 1).** On a default-input change (`AudioDeviceObserver`) or `.AVAudioEngineConfigurationChange` (the pinned device vanished), `resolveSwitch` re-selects; a `.switchTo` stops the engine, re-pins, rebuilds only the `AVAudioConverter` for the new input format, `rebind`s it into the existing `TapState` (so the `SessionAudioBuffer` and chunk `AsyncStream` survive), reinstalls the tap, and restarts — the transcript spans both devices. Switch is notified via `onDeviceSwitched` for the M9 HUD (logged `audio_device_switched`; the device name never hits `Log`, invariant 4).
- **Swift 6 concurrency:** `AudioDeviceObserver` is `@unchecked Sendable` so the HAL listener block can weak-capture it; the block hops `DispatchQueue.main.async` → `MainActor.assumeIsolated` before touching main-only state, mirroring the `FnHotkeyTap` assume-isolated pattern.

### M3-T2 code-review fixes (high, 8 findings)

- **`pin()` returns `Bool`; a switch is only reported when it took effect** (finding [0], confirmed). If the HAL device UID no longer resolves or `AudioUnitSetProperty` fails, `handleRouteChange` still keeps capture alive (invariant 1 — no session drop) but records the OS fallback in `currentDevice` and logs `audio_device_switch_pin_failed` instead of firing `onDeviceSwitched`/`audio_device_switched` — so the M9 HUD never claims a switch that didn't happen.
- **`engine.reset()` after every pin, before reading `inputFormat`** ([1]/[2]/[7], plausible). Forces the input node to re-read the newly-pinned device's native format so the converter/tap aren't built from a stale (previous-device) format → garbled post-switch audio.
- **Device switch builds a new `TapState` carrying the buffer over, rather than mutating `converter`** ([4], plausible). Keeps `TapState.converter` a `let` so the `@unchecked Sendable` justification stays "immutable + tap-thread-local only" — no main-thread write racing a possibly-in-flight tap callback. `carryOverBuffer()` is read on main only after `engine.stop()`+`removeTap`; `firstChunkLogged` is seeded from the carried buffer so latency isn't re-logged post-switch.
- **`AudioDeviceObserver` caches the device snapshot (+ UID→AudioDeviceID map), warmed at launch and refreshed on HAL change** ([5]/[8], plausible). The hotkey path (`start()`/`pin()`) now reads devices in memory instead of firing a burst of synchronous `AudioObjectGetPropertyData` round-trips inside the FR-01 ≤200ms budget.
- **`snapshot`/`refresh` resolve the system default by matching its `AudioDeviceID` against the map already built, dropping a redundant per-call UID round-trip** ([6], confirmed).
- **UserDefaults key centralized in `AppDefaultsKey.preferBuiltInMic`** ([10]) so the M10 Settings UI can't desync on a typo'd literal.
- **Not changed:** `AudioDeviceObserver`'s main-actor discipline is enforced by convention + `@MainActor` on its API, not by making the class `@MainActor` ([9]) — consistent with the accepted `FnHotkeyTap`/`TapState` `@unchecked Sendable` pattern; a full actor conversion fights the nonisolated `deinit` that must remove the HAL listeners.

## 2026-07-05 (session 6 — M2-T1 Fn hotkey)

- **Hotkey split: pure engine in KoeCore + CGEventTap in the app target** (mirrors the STT `WebSocketChannel` seam). `HotkeyEngine` (hold/toggle → start/stop, key-repeat/spurious-transition idempotent) and `FnKey` (keycode 63 + `maskSecondaryFn` → `.down`/`.up`) are pure and unit-tested (+20 tests); `App/FnHotkeyTap.swift` is the thin, untestable adapter that owns the real tap. Keeps activation semantics testable without synthesizing system events.
- **Tap callback runs on the main run loop; `MainActor.assumeIsolated` (no async hop).** The source is installed on `CFRunLoopGetMain()`, so the `@convention(c)` trampoline is always on the main thread — asserting isolation avoids a dispatch hop on the press→recording latency path (FR-01). `@preconcurrency import CoreGraphics` silences the spurious non-`Sendable` `CGEvent` diagnostic across that boundary.
- **Immediate `tapDisabled*` re-enable included in M2-T1; the 60s liveness timer + revocation → ⚠︎ re-guidance stay M2-T2.** Without the inline re-enable the tap silently dies on the first timeout, which would make the M2-T1 manual QA (Fn hold triggers callbacks) flaky. The periodic verification/revocation handling is genuinely M2-T2 and left there.
- **No `deinit` teardown on `FnHotkeyTap`.** The single instance is owned by `AppDelegate` for the whole app lifetime; a nonisolated `deinit` cannot touch the `@MainActor` tap/source state anyway. Teardown lives in `stop()`.
- **Tap mask is `flagsChanged`-only in M2-T1, not the plan's `keyDown|keyUp|flagsChanged`.** M2-T1 consumes only the Fn key (a `flagsChanged` event); subscribing to key-down/up would route every system-wide keystroke through our main-thread callback before the M2-T2 alt hotkey exists to use them. The two are added back with the alt-hotkey binding. (Post-review cleanup finding.)
- **Re-enable path calls `engine.reset()`.** A tap disabled mid-hold can miss the Fn key-up, latching `isActive` true; the `tapDisabled*` recovery now resets the engine (emitting `.stop` if needed) so recording state can't stick on. (Post-review correctness finding.)

## 2026-07-05 (session 5 — M4 follow-up code-review fixes)

## 2026-07-05 (session 5 — M4-T1/T2 Speechmatics STT adapter)

- **`STTClient` protocol in KoeCore, `SpeechmaticsClient` adapter in KoeProviders** — mirrors the LLM split (`LLMClient`/`GeminiClient`). Delivered M4-T1 + M4-T2 in one PR (as M6-T1 did protocol+adapter together). Built Speechmatics as the design's provisional primary; keys are Keychain-validated, so S2's formal A/B stays a separate later task (STATUS M4-T2 was `blocked(S2 decision)` only for the A/B, not for building the primary).
- **The design's `ForceEndOfUtterance` message does not exist in Speechmatics RT v2** (verified via context7 on the current SDK). RT v2's client→server terminator is `EndOfStream { last_seq_no }`; the VAD-based `conversation_config.end_of_utterance_silence_trigger` → server `EndOfUtterance` is a different feature and not for push-to-talk. Koe is push-to-talk (key-up = definitive end, no VAD per non-goals), so `endUtterance()` sends `EndOfStream`, which flushes the remaining finals; the stream ends on `EndOfTranscript`. One socket = one utterance; the next `prewarm`/`beginUtterance` opens a fresh socket.
- **WebSocket transport is a seam (`WebSocketChannel`)** so the wire protocol (StartRecognition config, `additional_vocab` mapping, invariant-8 absence of formatting options, partial→final parsing, `EndOfStream` seq_no) is unit-tested deterministically with a fake actor — no network, CI stays keyless/green. Real impl `URLSessionWebSocketChannel` verifies the connection with a ping in `prewarm` (surfaces auth/handshake failure before the first audio frame; 401/403 → `STTError.auth`).
- **Adapter is an `actor`** (unlike stateless `GeminiClient`): it owns the socket, the send seq counter, and the event-stream continuation. The receive loop is a nonisolated `Task` touching only Sendable values (channel + continuation), so audio `send` interleaves with receiving.
- **Endpoint default `wss://eu2.rt.speechmatics.com/v2`, `operating_point: enhanced`, `max_delay: 1.0` — provider-specific, so they live as adapter defaults, not in `KoeConstants`** (which is provider-neutral). Japan RTT (~220ms to EU) and `max_delay` are `[tune in Phase 0 / S2]`.
- **`additional_vocab` from `[STTVocabTerm]`**: readings normalized to full-width katakana in the adapter (hiragana→katakana + half-width→full-width), capped at 1,000 (`Log`s the count, no body text). invariant 8: no `enable_entities`/`punctuation_overrides`/`output_locale` sent — asserted by a test.

## 2026-07-04 (session 3 — M1-T2)

- **Coordinator seams are stage-named, not client-named.** M1-T2's plan lists an `STTClient` seam, but M4-T1 defines the richer streaming `STTClient` protocol. To avoid two conflicting protocols, the coordinator's seam is `Transcribing` (audio → transcript); an M4 `STTClient` adapter will satisfy it. Same for the other stages (`AudioCapturing`, `Formatting`, `TextInserting`, `HistoryWriting`, `ContextProviding`).
- **`UtteranceContext { index }` threaded through every stage.** Gives stages a stable FIFO id for logging/metrics and makes overlap ordering deterministically testable (the id is fixed at reserve time, independent of concurrent scheduling).
